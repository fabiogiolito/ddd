Doc-driven development

ddd is a skill for AI coding agents. You ask for what you want, as you already do. The agent writes it down in plain-language markdown docs first, then writes the code to match. The docs become a readable record of how the app works and how it changed.

The idea

The code is not the point anymore

AI agents now write most of the code, and most people building with them no longer read it. What still matters is how the app works and what it does. That is a question of behavior, and behavior is best expressed in natural language.

So ddd moves the source of truth. Docs describe the app; the code is treated like build output, generated from the docs and regenerated when they change. You can still open the code, but you don't have to.

You don't have to write the docs either. You keep talking to the agent the way you do now. For every request, it updates the docs first, then the code. The docs are how you follow what the agent is doing, and they stay behind as reference for how the app works. You can edit them directly when that's quicker, but nothing requires it.

You decide

What the app does, who can do what, the rules, the screens. You say it in chat; you can read it, and change it if you like, in the docs.

The agent handles

Writing the docs, then the code, tests, framework choices and plumbing, and keeping all of it consistent with the docs.

Changes anyone can follow

Because every change lands in the docs first, the history of the docs is a history of the app in plain language. Teammates can review a new feature or a changed rule by reading a doc diff ("guests who are going can bring one plus-one") instead of decoding a code diff. That includes people who don't code: product managers, designers, the person who asked for the tool.

Structure

A folder of linked docs

Everything lives in docs/. Each folder answers one question, so there's always one obvious place to look. Docs link to each other with [[wiki-links]], and frontmatter records what each doc depends on. Pick a file to read it.

# Bring a plus-one

Guests who are going can bring one person
with them.

## Rules
- Guests who are going can add one
  plus-one, by name.
- A plus-one takes a seat. If there's room
  for the guest but not the plus-one, both
  join the waitlist.
- Plus-ones show on the guest list under
  who brought them.

- "Each invite is for one person" no
  longer applies.
- An RSVP gets a plus-one field: their
  guest's name, if any.
- [[components/guest-list]] lists plus-ones
  under their guest.

## Acceptance criteria
- Given a guest going with a plus-one,
  then "seats left" drops by two.
- Given one seat left, when a guest replies
  going with a plus-one, then both join
  the waitlist.

## Open questions
- Can a host turn plus-ones off for a dinner?

Workflow

Docs first, then a plan, then the code

Most changes start as a message to the agent. It finds the docs the change belongs in, updates them, explains what that means for the app, and asks before touching the code. Here the request matches something already on the roadmap, so the agent builds that plan instead of starting from scratch.

If you edit a doc yourself

This is optional, but sometimes it's the quickest way to fix a rule or reword a label. No server watches your files. At the start of every turn the agent runs a status check that compares docs/ against the last build. If you changed something, even in another editor and without mentioning it, the agent sees the diff, checks which other docs it affects, and proposes the same kind of plan.

The rules the agent follows

  1. Docs first. Every change that affects behavior lands in docs/ before it lands in code. The agent turns each request in chat into a doc edit.
  2. Plan, then apply. The code is never rebuilt silently. The plan leads with what changes for users, not which files change.
  3. Behavior, not implementation. Docs say what happens, in words you'd use in a meeting. Technical detail goes in .tech/.
  4. Acceptance criteria are the contract. Each feature ends with Given / When / Then lines, which become tests. They pin down what the prose means.
  5. Open questions stop the build. If a doc leaves something undecided, the agent asks instead of guessing.
  6. Contradictions are surfaced. If two docs disagree, the agent asks which one wins.

Planning

Plan the whole app, build one feature at a time

The docs can describe what the app will do, not only what it does today. Describe everything you have in mind and the agent writes it up as planned features, grouped into phases, without building anything. Then it works through them one at a time.

Each feature has a status

StatusMeaning
ideaWorth remembering, not committed to. Can be a few lines.
plannedCommitted to, with rules and acceptance criteria written, so it's ready to build
in-progressBeing built now, one at a time
doneBuilt, with its acceptance tests passing

The status lives in the feature doc's frontmatter. The order lives in roadmap.md: each phase is a checklist of features and plain tasks, top to bottom, with an Ideas list at the end for things not yet scheduled. Phase 1 is the smallest version someone would actually use. Open roadmap.md in the file browser above to see one.

Working through it

Each /ddd next takes the next unchecked item through the same docs → plan → code loop: mark it in progress, ask any open questions, build it, run its tests, mark it done and check it off. Then the agent reports and stops.

Changing a feature that's already built

A built feature's doc describes only what's live, so you can trust every rule in it. Planned work that will change it lives in a doc of its own until it's built. There are two kinds, both in the file browser above:

  • An extension is a new feature that builds on an existing one, like . It says extends: [features/rsvp], describes the new behavior, and lists what will change in the RSVP doc.
  • A change adjusts how a built feature works, like . It says changes: [features/rsvp] and spells out what's true now and what will be true after.

Both go on the roadmap like any other item. When one is built, the agent writes it into the docs it targets, which produces the doc diff in the Review section above, and marks the plan done. Plans aren't deleted: they stay as the record of why a rule changed. If the RSVP doc changes before a plan is built, the status check flags the plan so it gets re-checked against the current rules.

A few rules keep the plan honest:

  • At the end of each phase the agent stops, even if you told it to keep going, so you can try the app before the next phase.
  • Anything new that comes up mid-build becomes its own roadmap item, not a quiet addition to the current one.
  • Asking for a new feature in chat gets one question: build it now, or add it to the roadmap?
  • Editing a planned feature is a plan-only change: the docs update, and no code is touched.

Change tracking

How the agent knows what changed

The skill includes a small Python script, standard library only. It keeps a hash and a copy of every doc as it was at the last build, in docs/.state.json and docs/.state/.

CommandWhat it does
statusDocs added, changed or removed since the last build; which other docs link to them; broken links. Edits to unbuilt features are listed as plan only
diff <doc>Line diff of one doc against its last built version
mark-appliedRecords the current docs as built, after the code and tests pass
restore <doc>Puts a doc back to its last built version
roadmapProgress per phase, plus anything out of sync: an item checked but not done, a planned feature missing from the roadmap
nextThe item to work on: the one in progress, or the first unchecked one

Install

Add it to your agent

Claude Code

Copy the ddd/ folder from the repo into ~/.claude/skills/, or into .claude/skills/ in one project. Then use /ddd.

Claude (web and desktop)

Download ddd.skill and add it under Customize > Skills.

Other agents

Point the agent at ddd/SKILL.md. It's plain markdown, and the script runs anywhere Python does.

Usage

/ddd on its own reports what changed in the docs. /ddd plan <idea> plans features and phases without building. /ddd next builds the next roadmap item. /ddd roadmap shows progress. Anything else after /ddd is a request: start an app or make a change.
