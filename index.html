Doc-driven development

ddd is a skill for AI coding agents. You ask for what you want, as you already do. The agent writes it down in plain-language markdown docs first, then writes the code to match. The docs become a readable record of how the app works and how it changed.

The idea

The code is not the point anymore

AI writes the code now, and most of us no longer read it. What still matters is what the app does, and that's best said in plain language.

So ddd makes the docs the source of truth. You keep asking the agent for what you want; it updates the docs first, then the code. You don't have to write or edit the docs, but you can read them to follow along, and so can anyone on your team.

You decide

What the app does, who can do what, the rules, the screens.

The agent handles

The docs, the code, the tests, and keeping them in sync.

Structure

A folder of linked docs

Everything lives in docs/. Each folder answers one question, so there's always one obvious place to look. Docs link to each other with [[wiki-links]], and frontmatter records what each doc depends on. Everything outside plan/ is built and live; everything inside it isn't built yet. # Reply to an invite

A guest opens their invite and says
whether they're coming.

## Who
- Anyone with the invite link.
- Guests don't need an account. They give
  their name and email once.

## Rules
- Replies close when the dinner starts.
- Each invite is for one person.
- If the dinner is full, new "going"
  replies join a waitlist.

## After
- Host gets [[integrations/email#new-reply]]

## Acceptance criteria
- Given a dinner with seats left, when a
  guest replies "going", then they appear
  on the guest list.
- Given a full dinner, when a guest
  replies "going", then they join the
  waitlist.

## Open questions
- Should guests see who said maybe?

# Bring a plus-one

Guests who are going can bring one person
with them.

## Rules
- Guests who are going can add one
  plus-one, by name.
- A plus-one takes a seat. If there's room
  for the guest but not the plus-one, both
  join the waitlist.
- Plus-ones show on the guest list under
  who brought them.

## Changes to rsvp
- "Each invite is for one person" no
  longer applies.
- An RSVP gets a plus-one field: their
  guest's name, if any.
- [[components/guest-list]] lists plus-ones
  under their guest.

## Acceptance criteria
- Given a guest going with a plus-one,
  then "seats left" drops by two.
- Given one seat left, when a guest replies
  going with a plus-one, then both join
  the waitlist.

## Open questions
- Can a host turn plus-ones off for a dinner?

Workflow

Docs first, then a plan, then the code

Most changes start as a message to the agent. It finds the docs the change belongs in, updates them, explains what that means for the app, and asks before touching the code. Here the request matches something already on the roadmap, so the agent builds that plan instead of starting from scratch.

If you edit a doc yourself

This is optional, but sometimes it's the quickest way to fix a rule or reword a label. No server watches your files. At the start of every turn the agent runs a status check that compares docs/ against the last build. If you changed something, even in another editor and without mentioning it, the agent sees the diff, checks which other docs it affects, and proposes the same kind of plan.

The rules the agent follows

  1. Docs first. Every change that affects behavior lands in docs/ before it lands in code. The agent turns each request in chat into a doc edit.
  2. Plan, then apply. The code is never rebuilt silently. The plan leads with what changes for users, not which files change.
  3. Behavior, not implementation. Docs say what happens, in words you'd use in a meeting. Technical detail goes in .tech/.
  4. Acceptance criteria are the contract. Each feature ends with Given / When / Then lines, which become tests. They pin down what the prose means.
  5. Open questions stop the build. If a doc leaves something undecided, the agent asks instead of guessing.
  6. Contradictions are surfaced. If two docs disagree, the agent asks which one wins.

Planning

Plan the whole app, build one feature at a time

The docs can describe what the app will do, not only what it does today. Describe everything you have in mind and the agent writes it up as plans in plan/, grouped into phases, without building anything. Then it works through them one at a time.

The folder shows the stage

StageWhere it lives
Ideaplan/ideas/, a few lines, not committed and not on the roadmap
Plannedplan/, with rules and acceptance criteria written, on the roadmap
In progressplan/, marked status: in-progress, one at a time
Builtfeatures/, data/, pages/, and the rest

So you can tell what's built and what's coming from the folder tree, without opening anything. The order lives in roadmap.md: each phase is a checklist of plans and plain tasks, top to bottom. Phase 1 is the smallest version someone would actually use. Open to see one. Ideas aren't on it; is the list of them, and promoting one means moving it up into plan/ and adding it to the roadmap.

Working through it

Each /ddd next takes the next unchecked item through the same docs → plan → code loop: mark it in progress, ask any open questions, build it and run its tests. Then its doc moves out of plan/ to where it now belongs, the roadmap item is checked off, and the agent reports and stops.

Changing a feature that's already built

A built feature's doc describes only what's live, so you can trust every rule in it. Work that will change it is a plan of its own in plan/, until it's built. There are two kinds, both in the file browser above:

  • An extension adds a capability on top of a built feature, like . It says extends: [features/rsvp], describes the new behavior, and lists what will change in the RSVP doc.
  • A change adjusts how a built feature works, like . It says changes: [features/rsvp] and spells out what's true now and what will be true after.

When one is built, the agent writes it into the docs it targets, which produces the doc diff in the Review section above. The plan then moves to plan/done/ as the record of why the rule changed. If the RSVP doc changes before a plan is built, the status check flags the plan so it gets re-checked against the current rules.

A few rules keep the plan honest:

  • At the end of each phase the agent stops, even if you told it to keep going, so you can try the app before the next phase.
  • Anything new that comes up mid-build becomes its own plan or idea, not a quiet addition to the current one.
  • Asking for a new feature in chat gets one question: build it now, or add it to the roadmap?
  • Editing anything in plan/ is a plan-only change: the docs update, and no code is touched.

Change tracking

How the agent knows what changed

The skill includes a small Python script, standard library only. It keeps a hash and a copy of every doc as it was at the last build, in docs/.state.json and docs/.state/.

CommandWhat it does
statusDocs added, changed or removed since the last build; which other docs link to them; broken links. Edits inside plan/ are listed as plan only, and plans whose target changed are flagged to re-check
diff <doc>Line diff of one doc against its last built version
mark-appliedRecords the current docs as built, after the code and tests pass
restore <doc>Puts a doc back to its last built version
roadmapProgress per phase, plus anything out of sync: an item checked but still in plan/, a plan missing from the roadmap, a link to a doc that moved
nextThe item to work on: the one in progress, or the first unchecked one

Install

Add it to your agent

With the skills CLI, from your project folder (needs Node 22.20 or later):

npx skills add fabiogiolito/ddd

It asks which agents to install it for: Claude Code, Cursor, Codex and others. Add -g to install it for every project, or -a claude-code -y to skip the questions. npx skills update ddd gets the latest version.

Claude (web and desktop)

Download ddd.skill and add it under Customize > Skills.

By hand

Copy skills/ddd/ from the repo into .claude/skills/ in a project, or ~/.claude/skills/ for all of them. Other agents can read skills/ddd/SKILL.md directly; it's plain markdown.

Usage

/ddd on its own reports what changed in the docs. /ddd plan <idea> writes plans and phases without building. /ddd next builds the next roadmap item. /ddd roadmap shows progress. Anything else after /ddd is a request: start an app or make a change.
