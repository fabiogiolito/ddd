Doc-driven development

ddd is a skill for AI coding agents. You describe an app in a folder of plain-language markdown docs. The agent writes the code from those docs and keeps it in sync whenever they change.

The idea

The code is not the point anymore

AI agents now write most of the code, and most people building with them no longer read it. What still matters is how the app works and what it does. That is a question of behavior, and behavior is best expressed in natural language.

So ddd moves the source of truth. Docs describe the app; the code is treated like build output, generated from the docs and regenerated when they change. You can still open the code, but you don't have to.

You own

What the app does, who can do what, the rules, the screens, the data it keeps. Written as you'd explain it to a colleague.

The agent owns

The code, the tests, the framework choices and the plumbing. It keeps all of that consistent with the docs.

This also makes an app readable by people who don't code: product managers, designers, the person who asked for the tool. They can read how it works and change it by editing a sentence.

Structure

A folder of linked docs

Everything lives in docs/. Each folder answers one question, so there's always one obvious place to look. Docs link to each other with [[wiki-links]], and frontmatter records what each doc depends on. Pick a file to read it.

Workflow

Docs first, then a plan, then the code

A change can start from a message to the agent or from editing a doc directly. Either way it goes through the docs first. The agent updates them, explains what that means for the app, and asks before touching the code.

When you edit a doc yourself

No server watches your files. At the start of every turn the agent runs a status check that compares docs/ against the last build. If you changed something, even in another editor and without mentioning it, the agent sees the diff, checks which other docs it affects, and proposes the same kind of plan.

The rules the agent follows

  1. Docs first. Every change that affects behavior lands in docs/ before it lands in code. A request in chat becomes a doc edit.
  2. Plan, then apply. The code is never rebuilt silently. The plan leads with what changes for users, not which files change.
  3. Behavior, not implementation. Docs say what happens, in words you'd use in a meeting. Technical detail goes in .tech/.
  4. Acceptance criteria are the contract. Each feature ends with Given / When / Then lines, which become tests. They pin down what the prose means.
  5. Open questions stop the build. If a doc leaves something undecided, the agent asks instead of guessing.
  6. Contradictions are surfaced. If two docs disagree, the agent asks which one wins.

Change tracking

How the agent knows what changed

The skill includes a small Python script, standard library only. It keeps a hash and a copy of every doc as it was at the last build, in docs/.state.json and docs/.state/.

CommandWhat it does
statusDocs added, changed or removed since the last build; which other docs link to them; broken links
diff <doc>Line diff of one doc against its last built version
mark-appliedRecords the current docs as built, after the code and tests pass
restore <doc>Puts a doc back to its last built version

Install

Add it to your agent

Claude Code

Copy the ddd/ folder from the repo into ~/.claude/skills/, or into .claude/skills/ in one project. Then use /ddd.

Claude (web and desktop)

Download ddd.skill and add it under Customize > Skills.

Other agents

Point the agent at ddd/SKILL.md. It's plain markdown, and the script runs anywhere Python does.

Usage

/ddd on its own reports what changed in the docs. /ddd followed by a request starts a new app or makes a change.
